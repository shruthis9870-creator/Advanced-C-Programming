Why this stands out

Rendering then silently drops any points outside the canvas in plotPoint(), so the object data and the picture can disagree.

Why fixing it helps
This editor should reject invalid shapes at the input boundary, not carry impossible geometry through the rest of the program.
Enforcing the canvas contract will make the displayed picture match the stored object list and keep redraw cost bounded by the actual canvas size.

Explanation:
Why this stands out
The review examined readInt() because every menu choice, object id, coordinate, and radius flows through that single function.
Its current parsing strategy accepts the numeric prefix of a malformed token and leaves the remaining characters behind for the next prompt.
What this means in practice
If a user enters something like a number followed by extra characters, the first prompt succeeds but the leftover text is consumed by the next prompt, which makes the interaction confusing and error-prone.
If standard input reaches end-of-file, the function never exits its loop, because it keeps treating EOF like a retryable format error.
That makes redirected input, automated testing, or accidental terminal EOF behave badly.
Why fixing it helps
Input parsing is a core contract for this CLI. Each prompt should consume exactly one user response, and unrecoverable input failure should stop the current operation cleanly.
Making parsing strict here will improve every menu path at once.
